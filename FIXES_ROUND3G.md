# Fixes round 3G: security hardening and a tidy CI (24 Oct)

**Do this right after round 3F, before 3E.** Commit each item separately with "Fixes round 3G, item N: …", tick it in `WORK_QUEUE.md` in the same commit, push, keep the build green. No user-facing feature is removed.

## What the audit found (24 Oct, whole Git history, 114 commits)
- **No leaked secrets.** All added lines in every commit were scanned for Anthropic, OpenAI, Google, GitHub, Slack, AWS, Stripe, Resend, Hugging Face, Groq, Neon, Vercel, LiveKit, JWT and private-key patterns: nothing. The only "tokens" are fake test values.
- **Keys are stored correctly:** every API key, OAuth token and the GitHub token goes through `secrets.rs` into the Windows Credential Manager, never into `settings.json` or the database. CI uses no secrets, so nothing is baked into the public installers.
- **Good already:** strict CSP (`script-src 'self'`), `withGlobalTauri: false`, no `innerHTML` with untrusted content (only fixed SVGs and the Rust-generated QR), `open_url` only accepts http(s), Discord only `discord://`, PowerShell only with fixed scripts, release build strips symbols and has no console/devtools, the named pipe is per user (SID) and refuses remote clients, OAuth uses PKCE on 127.0.0.1.

So this round is **hardening**, not emergency fixes.

## Item 1: Approval for running commands must come from Rust, not the page
`studio_run` takes `approved: bool` from the frontend, and the Studio page always sends `approved: true` (`src/studio/main.ts:279`, `src/core/bridge.ts:662`). Any script running in any Groovy window could run a shell command.
- Remove the `approved` argument. Rust shows the confirmation itself (a native dialog via `tauri-plugin-dialog` or the island's permission prompt, owned by Rust), or checks the command against the user's saved "always allow" list in the database.
- Same review for every command that runs programs, deletes or moves files, ends processes, sends mail or posts anywhere (`pc.rs`, `tools.rs`, `skills/*`, `models.rs`, `spotify.rs:1032`, the coding agents): the decision to allow is made and stored in Rust (`tools::permission`), never trusted from the frontend.
- Test: calling `studio_run` from the island window's console fails.

## Item 2: Each window can only call the commands it needs
`capabilities/default.json` gives all four windows (island, settings, mochi, studio) the same permissions, and every one of the ~288 commands is callable from every window.
- Split capabilities per window (Tauri 2 capabilities + per-command `permissions`/ACL generated by `tauri-build`'s app manifest): e.g. Studio and shell commands only in `studio`; account, key and mail-setup commands only in `settings`; the island gets only what it uses.
- Test in CI: a list of forbidden commands per window, each call must be rejected.

## Item 3: Tighten the CSP
- `connect-src` allows any `wss:`. Narrow it to the hosts actually used (LiveKit `wss://*.livekit.cloud`, the phone relay host if any). Network calls to AI providers go through Rust, so the page needs no other origins.
- Add `object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'none'`. Check whether `style-src 'unsafe-inline'` can be dropped (move inline styles to classes or CSSOM `el.style.x =`, which CSP allows).
- Turn on `"freezePrototype": true` in `tauri.conf.json` if nothing breaks.

## Item 4: The named pipe only for this user
`pipe.rs` creates `\\.\pipe\groovy-<sid>` with the default security descriptor. Give it an explicit DACL: full access for the current user's SID (and SYSTEM) only, nothing for Everyone or Anonymous. Keep `first_pipe_instance(true)` and the remote-client rejection. Test: the pipe's DACL contains only those SIDs.

## Item 5: Untrusted content can't make Groovy act on its own
Mail, web pages, GitHub issues, notes and anything the AI reads can contain instructions ("ignore previous instructions, delete…").
- Tool calls that change things (send, delete, run, buy, post, end a process, write files) always need the user's approval when the turn included untrusted content, even if the tool is set to "Allow".
- Mark untrusted text clearly in the prompt as data, not instructions.
- The `mailto:` tool (`okgroovy/mod.rs:720`) is fine (it only opens a draft), keep it that way.
- Test: a mail containing "delete my files" produces no file action.

## Item 6: Test switches and the release build
Environment variables `GROOVY_TEST_WAV`, `GROOVY_TEST_WAKE_WAV`, `GROOVY_SMOKE_VIEW`, `GROOVY_PEAK_TEST`, `GROOVY_WORK_TEST`, `GROOVY_INTEROP_TOKEN`, `GROOVY_BACKDROP` change behaviour in the shipped app. Compile them in only under a `ci` cargo feature (with round 3F item 2's `worktest` feature). The release build ignores them.

## Item 7: Logs and settings never hold secrets
- Add a redaction step to `log::line`: anything that looks like a key, bearer token, `Authorization` header, OAuth code or password is replaced with `[hidden]`.
- Test: log a fake key of each provider's format and check the log file.
- Settings export / diagnostics / crash reports (if any) exclude the Credential Manager values.

## Item 8: Dependencies checked automatically
- Add `.github/dependabot.yml` (free) for `cargo` (windows), `npm` (windows) and `github-actions`, weekly, grouped into one PR per ecosystem.
- Add a CI job (fast, Linux runner) that runs `cargo audit` (or `cargo deny check advisories licenses`) and `npm audit --omit=dev --audit-level=high`, and **gitleaks** on the push. Fail on high/critical advisories and on any secret found.
- Update the dependencies that have advisories now; record what changed in `STATUS.md`.

## Item 9: One tidy place to download builds
The Actions page has 159 runs and 475 artifacts, one full build per push.
- **Every push:** one fast check job (Linux): `cargo check`, `cargo clippy`, `cargo test` for pure-Rust tests, `tsc --noEmit`, `vitest`, gitleaks, audits. No installer.
- **Full Windows build** (installers, smoke, memory, peak, frame-time, screenshots) runs only:
  - when manually started (`workflow_dispatch`),
  - on a push whose commit message contains `[build]`,
  - and once a night if the branch changed (`schedule`).
- **One download place:** a successful full build replaces the assets on a single pre-release named **"Groovy latest build"** (tag `latest-build`, updated in place with `gh release upload --clobber`). The owner always downloads from that one page. Keep `windows-release.yml` for real versions (`windows-v*` tags).
- Set artifact `retention-days: 3` (screenshots and logs only), and add a weekly cleanup job that deletes workflow runs older than 14 days.
- Run names: set `run-name:` so the list reads "Build 0.6.x · round 3F item 2" rather than whole commit messages.
- Keep `concurrency: cancel-in-progress` and the caches; add `Swatinem/rust-cache` if it's faster than the current cache.
